# Operational Continuity Contract — {{PROJECT_NAME}}

Continuity contract for Hermes sessions working on this repo. Based on the experience
report ADR-0021 (`HermesVPS2`). Fill in the values between `{{...}}` for the target
project, then remove this comment.

## Authoritative state files

The state of ongoing work must be persisted in:

- `docs/operations/CURRENT.md`   — active task state, updated at every checkpoint
- `docs/operations/HANDOFF.md`   — written only on context-pressure exit or planned rotation
- `docs/operations/ACTIVITY.md`  — append-only checkpoint log
- `BACKLOG.md`                   — ticket state (create if this repo tracks its own tickets)
- `CHANGELOG.md`                 — user-visible / architectural / operational changes only

## Definition of Done

A subtask is not complete until:

1. its implementation has been verified (real command output, not assumed) — for a file write, see "Write verification" below;
2. `docs/operations/CURRENT.md` has been updated;
3. `BACKLOG.md` reflects the new state (if applicable to this repo);
4. `CHANGELOG.md` has been updated when the change is user-visible, architectural,
   operational, or released;
5. the next executable action has been recorded;
6. modified files and unresolved risks have been recorded.

## Write verification (mandatory)

`write_file` calls on sizeable content (roughly above ~1 KB, or any text with embedded
quotes, backticks, or newlines) can **fail silently** on some Hermes installations: a
known tool-call argument sanitizer failure mode replaces unparseable JSON with an empty
object and drops the write — no exception, no visible error in the conversation. Reported
upstream: NousResearch/hermes-agent#119389 (surfaced via the `HermesVPS2` incident, ADR-0021 lineage).

After every `write_file` on one of the Authoritative state files above, or any file
> ~1 KB, immediately `read_file` it back and confirm the new content is present. A write
is not "verified" (Definition of Done, item 1) until this read-back has been done. If the
read-back shows stale content, treat the write as failed: retry once, then fall back to
`terminal`/`execute_code` for that write.

## Mandatory checkpoint boundaries

Checkpoint (update CURRENT.md + append ACTIVITY.md entry) after:

- completing a subtask;
- a successful test or validation milestone;
- before a large refactoring or destructive/infra operation;
- before launching a subagent or delegated task;
- after a tool failure that changes the execution plan;
- when context pressure reaches 55% (see thresholds below).

## Context-pressure behavior

Percentage thresholds are model-agnostic; absolute token counts are not. The limit that
matters is the one enforced by the **gateway** serving the session, not the model's native
window. Use the row of the gateway/model actually serving you (updated 2026-09-29 per ADR-0005,
verify periodically — keep in sync with `dev-factory/gateways.yaml`):

| Gateway / model | Context | Max output | 55% | 65% | 75% | 82% | 90% |
|---|---:|---:|---:|---:|---:|---:|---:|
| `hermes-orchestrator` — Qwen-3.8-27B-NVFP4 (dgx-spark, **default**) | 98,000 | 2,000 | ~53,900 | ~63,700 | ~73,500 | ~80,360 | ~88,200 |
| `anthropic/claude-sonnet-5` (escalation only, ADR-0004) | 1,000,000 | — | ~550,000 | ~650,000 | ~750,000 | ~820,000 | ~900,000 |
| `gpt-5.6-sol` (escalation only, ADR-0004) | 1,050,000 (922,000 max input) | — | ~577,500 | ~682,500 | ~787,500 | ~861,000 | ~945,000 |

The Claude Code roles (`cc-dev` 98k/4k, `cc-review` and `cc-test` 32k/2k) do not follow this
contract: they are short-lived, headless runs whose context is budgeted by
`scripts/orchestrate.py` (ADR-0005). Hermes never codes in a repo that has `.ai/orchestration.yaml`
— it uses the `sequential-coding-team` skill.

**2,000-token output cap:** a single response cannot carry a large file. Write tracking files
and task contracts in several small edits and verify each one (see Write verification).

Any other model: verify its real context window before trusting a number — never assume,
never reuse a figure measured against a different tokenizer (e.g. Sonnet 5's tokenizer
produces ~30% more tokens than Sonnet 4.6 for the same text — recount, don't extrapolate).

- **>= 55%** — checkpoint due if the repo changed since the last one. Update `CURRENT.md`.
- **>= 65%** — finish only the current atomic operation; do not start another subtask.
- **>= 75%** — closing mode: tools limited to read/write of tracking files, non-destructive
  validation, `git add`/`commit`. No new deployment, no new work branch, no massive
  refactor, no delegation, no destructive infra command.
- **>= 82%** — handoff only: write `docs/operations/HANDOFF.md`, light validation, commit
  if permitted.
- **>= 90%** — `CHANGELOG.md` must already be current — not deferred to end of task.

## Working outside any repo

If a session works outside this repo entirely (direct chat, cron, another machine), the
same discipline applies but the disk anchor changes: use a global, out-of-repo file (e.g.
`/opt/data/operations/HANDOFF.md`) instead of `docs/operations/HANDOFF.md` — a chat
transcript alone is not a reliable handoff mechanism, it can be lost to compaction.

## Prohibition

Do not merely state that documentation should be updated later. If the tracking files have
not been updated, report the work as incomplete — not "done, will document after".
